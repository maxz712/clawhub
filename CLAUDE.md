# ClawHub

GitHub, rebuilt from the ground up for AI agents. **Agents and humans are the same kind of thing — identities; merge rights are role-based and uniform (v3, 2026-07-06).** Agents write the bulk of the code; humans supervise by CONFIGURATION (roles + per-repo merge policy), not by a hardcoded kind gate. `docs/redesign-v3.md` + `docs/redesign-v3-plan.md` are the v3 source of truth where older docs conflict.

**Read `design.md` before implementing any new feature.** It is the source of truth for architecture, data model, trailer convention, and API specs.

**This repo deploys itself.** The canonical home is `xinmingzhang/clawhub` on the production instance (useclawhub.com) — a user-owned namespace; the `claude-code` agent is a granted writer that pushes the deploys. Merging a Change there runs `scripts/self-deploy.sh` on the production host and mirrors `master` to GitHub (`maxz712/clawhub`). Read `docs/operations.md` before touching production — it covers the merge-=-deploy flow, where secrets live, and the incident runbooks.

## Design Principles

- **Identities all the way down; merge rights are UNIFORM (v3).** Git HTTP push accepts an agent token (HTTP Basic username `agent-token`) **or** a user token (username = the human's handle); the password is the JWT either way. `middleware/auth.ts` `classify()`s the caller into a `PushActor` (`agent`|`user`); an agent push opens a Change with `changes.openedByAgentId` (+ `onBehalfOfUserId` — the sponsoring human, git author-vs-committer style), a human push with `changes.openedByUserId`. **WHO may merge is a ROLE question (`change:merge`, `requireMergeRights`), identical for humans and agents — an agent holding it merges at ANY risk once policy is satisfied. WHAT a merge requires is per-repo POLICY (`evaluateMerge` — approvals, review basis, CI, sensitive paths), evaluated with NO actor-kind input.** Supervision is a configuration posture: default roles hand agents no merge permission and default policy requires human code review at high risk / sensitive paths — but both are owner-editable. The old kind-keyed machinery (mergeActorIsAgent, allowAgentMergeWithoutCi, earned autonomy as the agent path to merge) is REMOVED.
- **Everything is git.** Standard git Smart HTTP. ClawHub adds value *after* the push — parsing trailers, routing reviews, running CI.
- **Agents describe their own work.** Commit trailers (`Intent:`, `Risk:`, `Scope:`, `Review-Focus:`, `Closes:`, `Agent:`) drive the UI. ClawHub never runs an LLM.
- **Focused review is the default.** Humans see only the lines agents flagged via `Review-Focus:` trailers, `// REVIEW:` inline comments, or reviewer agents. Full diff is one click away.
- **Auto-repo on first push.** No dashboard step needed before pushing. The first branch pushed becomes the repo's default branch.
- **Risk is computed; basis is recorded; defaults are conservative (v3).** Risk is COMPUTED from each change (`services/risk-engine.ts`) — path sensitivity, size, test coverage, author track record, deterministic, no LLM — and the declared `Risk:` trailer is only a floor. DEFAULT policy: medium+ risk requires a human approval; high/critical or sensitive paths require one with `basis: code` — but these are policy fields, not invariants: the sensitive-path baseline is default-on-but-editable (`sensitiveBaseline: false` disables), and `requireCiRun` is the uniform CI-strictness knob ("skipped" blocks everyone or no one). Approvals record their basis (`behavior` vs `code`). Full agent autonomy = grant a role with `change:merge` + set policy accordingly; verified autonomy (attestation satisfies a review slot) remains the policy-native path.
- **Review overhaul (2026-Q3) — "inference informs, determinism decides."** The decided direction + build plan live in `docs/review-overhaul-strategy.md` + `docs/review-overhaul-plan.md`: a deterministic focus floor for trailer-less pushes, a native platform-keyed ADVISORY reviewer behind an API-side metering gateway (platform key never enters containers), spec-basis conformance verify (issue → description → inferred, gate-aware), plan-then-playback cheap verify, metered billing, and the one-click autonomous Loop. **Custody correction to the "ClawHub never runs an LLM" bullets below:** ClawHub now DOES run first-party inference for its OWN system agents (the native reviewer + verifier), but ONLY through the custody gateway — the platform key is read solely in the API process and never enters a container. Tenant BYO agents + agent memory are still the tenant's own model (ClawHub orchestrates the hands). The deterministic merge gate / risk / attestation guarantees are unchanged — inference only ever INFORMS. **Q4 items are built too (2026-07-05):** GitHub App mirror-and-verify, model-catalog GA (public `GET /api/v1/public/llm-catalog`, per-repo review-model pin in Settings, org provider allowlist `organizations.llm_provider_allowlist` (migration 0056) enforced at the gateway, `scripts/verify-bench.ts`), visual base/head/diff triptych in EvidencePanel, platform-key (zero-setup) Loops (`installLoop keySource:'platform'` + mandatory budget row), validated `config`/`migration` verify claims, and the dark-until-`CLAWHUB_DEMO_REPO` live demo endpoint (`/api/v1/public/demo/*`).
- **D8/D9/D10 (2026-07-03) — open-model routing + tier lineup + sized spend caps.** **D8:** platform-keyed open-model traffic runs through OpenRouter PINNED to a named US-jurisdiction host (`provider.only` + `allow_fallbacks:false` + `data_collection:deny` + pinned quantization, FORCED server-side at the gateway so a container can't widen it), never a PRC first-party API; qualification is per (model, host, quantization); the subprocessor table names the HOST (`services/llm-catalog.ts`). **D9:** the router routes by capability tier, never vendor, resolving to TWO live US-pinned models with execution picked by MODE (review = single-shot, verify = agentic): **fast/review → `deepseek/deepseek-v4-flash`** (cheap single-shot review, the 95%); **balanced/verify + frontier/audit → `z-ai/glm-5.2`** (Fireworks, full precision, 1M ctx, clean agentic tool-caller) — it runs AGENTIC for verify (the browser loop) and SINGLE-SHOT when auditing a review, a DIFFERENT family from the V4-Flash primary = the cross-family audit diversity D9 wants. DeepSeek's thinking-mode tool-call trap (400 on a multi-turn tool loop, rejects tool_choice=required) is why **`run_review` is SINGLE-SHOT** (`entrypoint.sh:llm_oneshot` — one non-agentic completion straight to the gateway → the round-trip contract never fires, matching D9's "single-shot structured review") and why the only model that runs the agentic loop (GLM-5.2) is a clean tool-caller. DeepSeek V4 Pro + `qwen/qwen3-coder` stay cataloged (env-routable) but aren't defaults (V4 Pro can't run the agentic loop + adds no family-diversity over V4 Flash). **D10:** the sized cap set — free = per-TENANT 100 reviews/mo (summed across all repos), 10/day, ≤3 repos, 2M/120k tokens, 0 platform verify; pro = 250 reviews + 10 verify credits/seat; an atomic per-tenant Redis reserve (`services/platform-quota.ts`) closes the read-then-act race + the minted-repo hole; a mandatory Loop budget row auto-creates on the first agent-origin platform draw; a global `CLAWHUB_PLATFORM_GLOBAL_MONTHLY_CAP` (default $100) + a per-request 50k-input-token ceiling + per-commit dedup are the backstops. Platform-keyed VERIFY (`services/native-verifier.ts`, metered $2, `repositories.platformVerifyEnabled` opt-in, paid-plan + credit gated) makes `verify_credits` real. Migration 0049.

## Key Concepts

- **v3 redesign (2026-07-06, docs/redesign-v3.md + docs/redesign-v3-plan.md) — identities, RBAC, uniform merge rights, workflow runs, focused review, code graph.** Built across migrations 0060–0064: the identities PROJECTION over users+agents (`services/identities.ts`, People directory with common-context visibility, `PATCH /identities/self` profile edit, `audit_events.actor_handle`); generic RBAC (`services/permissions.ts` — 19 permission keys, implication table, `role_assignments` so humans hold roles too, org-scoped roles; agent roles = CEILINGS, human roles = ADDITIVE grants); the uniform merge gate (see Design Principles); default personal agent on register (dormant, Developer role, `ensurePersonalAgentInBackground`, kill switch `CLAWHUB_DISABLE_DEFAULT_PERSONAL_AGENT`); the CLAIM FLOW IS REMOVED; deterministic harness only (custom images 400; `CLAWHUB_ALLOW_CUSTOM_HARNESS_IMAGES=1` escape hatch; `standing_agents.exec_style` cli|api → `CLAWHUB_EXEC_STYLE`) — and the harness image a run EXECUTES is resolved at DISPATCH from `DEFAULT_HARNESS_IMAGE` (`resolveHarnessImage`), making `standing_agents.image` ADVISORY, so a republished `:latest` reaches every deployment on its next run (the column used to be frozen at create, silently pinning old rows to a host-local `clawhub-agent-harness:local` tag CI never rebuilds); model×mode gating (catalog `agentic` flag; `model_not_agentic` 400); thread slash commands (`services/slash-commands.ts` — a Change/Issue comment LEADING with /dev /review /verify /test /scout /triage /loop dispatches the workflow, humans-only + workflow:trigger, kill switch `CLAWHUB_DISABLE_SLASH_COMMANDS`); coalesce-to-latest leases (`services/run-leases.ts` — agent dispatches stamp `concurrencyGroup agent:<id>:<mode>:<resource>`; same-version dedupes, stale pending collapses); Workflow Runs surface (`routes/workflow-runs.ts`, `ci_runs.triggered_by_user_id`); Graphify code graph (`services/code-graph.ts`, default-on, NOT memory); scheduler tenant fair share (`CLAWHUB_TENANT_MAX_CONCURRENT_RUNS`). "Role" now means ACCESS CONTROL; the legacy agent-role templates are TEMPLATES (`/api/v1/templates` alias).
- **v4 (2026-07-06, docs/redesign-v4.md — SUPERSEDES v3 where they conflict): workflows own the work; identities live in one place.** Migration 0065. A DEPLOYMENT (`standing_agents`) is identity + role + provider ONLY — `repo_id` nullable, null (global) is the default; the target repo resolves AT DISPATCH (workflow scope / thread context; `dispatchStandingRun` `opts.repoId`). A **WORKFLOW** (`workflows` table, `services/workflows.ts`, `/api/v1/workflows`) owns instructions + trigger/cadence + optional repo scope (default all; fan-out cap `CLAWHUB_WORKFLOW_FANOUT_CAP=5`), is fully editable, and stamps `ci_runs.workflow_id` (its activity history). Templates are workflow PRESETS on the Workflows tab (`/api/v1/workflow-templates`), not a page. `/people/[handle]` is THE identity page (agents show management + activity there; `/agents/[id]` redirects). Any identity may belong to an org (`agents.org_id`, default none; `PATCH /agents/:id/org`). Agent runs are ACTIVITY (the run detail leads with produced artifacts — reviews, the Change), never CI plumbing. Hub = Overview·Keys·Workflows·Runs·Memory·Ops; Roles is TOP-LEVEL next to People; Standing/Fleet/Sandboxes/Templates tabs are gone.
- **Agents are created by humans** — `POST /api/v1/agents` REQUIRES a valid user Bearer riding along (association at registration); anonymous self-registration returns 401 unless the instance sets `CLAWHUB_ALLOW_UNCLAIMED_AGENT_REGISTER=1` (self-host/dev; the test suite sets it). The dashboard create flow is `POST /api/v1/agents/managed` (routes/agent-identity.ts): name + ACCESS ROLE + run-mode — `local` returns the token once; `deployed` creates one standing-agent row per pointed repo sharing ONE identity/token, key from the VAULT (`llm_keys`, sealed, many agents per key) or platform-metered (same N5/D10 gate as installLoop). **Access roles** (`access_roles` + `role_assignments`, `services/access-roles.ts` + `services/permissions.ts`; builtins Admin/Developer/Reviewer/Auditor seeded per user) are PERMISSION SETS + repo scope — enforced as a CEILING for agents at `checkPushRights` + `repoAccessFor`, ADDITIVE grants for humans; `change:merge` in a role grants merging at any risk, policy permitting. Roleless agents keep legacy grant behavior. Agent names are globally unique. **Workflows** are slash-flag prompts (`/dev` `/review` `/verify` `/scout` `/triage` `/loop`) expanded server-side at dispatch (`services/agent-workflows.ts`); run audit at `GET /agents/:id/runs` + the Workflow Runs surface. **Per-agent intelligence** (`agents.intelligence`: skills + MCP) rides in as `CLAWHUB_INTELLIGENCE`; the harness materializes it and owns deterministic repo dep setup (`setup_repo_deps`).
- **Personal agents + auto-claim** — `POST /api/v1/agents/personal` (user auth) find-or-creates the caller's one personal agent and returns a fresh token each call. `ch init` uses this so a logged-in human gets an auto-claimed agent in one command.
- **Claim flow — REMOVED (v3).** `/api/v1/agents/claim` + the claim-token rotate endpoint are gone; `agents.claim_token*` columns remain orphaned until a cleanup migration. Association happens at registration (user Bearer rides along) or via the dashboard create flow; wrapper identities replace claiming end-to-end. An agent's repos remain owned by its `service` user; a human takes direct ownership with `ch repo transfer`. Ownership lives in DB rows and is independent of who pushes.
- **Change** = PR equivalent. Created on git push from the branch head. States: `draft → pending → approved → merged` (also `changes_requested`, `rolled_back`). One Change per branch. **Draft (WIP) Changes** (`changes.isDraft`) are skipped by reviewers — a verify/review standing agent only runs on PUBLISHED diffs (`services/standing-agent-scheduler.ts` skips drafts; publishing emits `change.ready`, now in the `CHANGE_EVENTS` family, which re-dispatches it). Mark draft via a `Draft: true` commit trailer (`Draft: false`/absent publishes; the head commit's trailer wins, else the existing state is preserved — `post-push.ts`) or the API/CLI (`POST .../changes/:id/{draft,publish}`). Drafts also can't merge (`changes.ts`).
- **Computed risk + review basis + the UNIFORM gate (v3)** — `services/risk-engine.ts` computes each Change's risk deterministically (path sensitivity, size, missing tests, author rollbacks; no LLM) and persists `computedRisk` + `riskReasons`. Effective risk = `max(declared, computed)`. `services/merge-policy.ts` gates on it with NO actor-kind input: `ciRequired` defaults true (failing/in-flight CI blocks everyone); **`requireCiRun`** is the uniform strictness knob — when set, `skipped` (no pipeline) blocks EVERY merge actor; unset (default), `skipped` passes for everyone. At/above `codeReviewRequiredAtRisk` (default `high`) or on a forced/sensitive path, only human approvals with `basis: code|both` satisfy the gate (behavior-only blocks with `needs_code_review`). The gate re-evaluates fresh under the repo lock immediately before the git merge (`recomputeChangeCiStatus` also can't write a terminal change's `ciStatus`). WHO may merge is separate: `requireMergeRights` (write floor for all; role-holders need `change:merge`; role-less = legacy write-admits-merge). Sensitive paths (migrations, `*.sql`, `deploy/**`, `scripts/**`, `.clawhub/ci/**`, Dockerfile, compose, `.clawhub/policies/**`) require human code review BY DEFAULT via `sensitiveBaseline` (default true, editable — v3 demoted the baseline from non-removable floor to conservative default). **Approvals are pinned to the commit they approve (#121)**: a push that moves the head dismisses prior `approve` verdicts (`dismissStaleApprovals`, default true) — otherwise approving a benign diff and then pushing a sensitive one satisfied the code-review gate with code nobody read. See docs/governance.md + docs/redesign-v3.md §2.
- **Verified autonomy (opt-in)** — the ONE path by which an *agent* verdict can satisfy the human code-review gate: a per-repo `mergePolicy.verifiedAutonomy` ({`enabled`,`maxRisk`,`allowSensitivePaths`,`floorGlobs`}, OFF by default, safe-parsed in `normalizeMergePolicy`) lets a deployed **verify-mode** reviewer's end-to-end attestation stand in for the human approval up to `maxRisk`, with a configurable human-only `floorGlobs` backstop (default empty = full autonomy; `RECOMMENDED_VERIFIED_AUTONOMY_FLOOR_GLOBS` is the safe preset). The "verified" signal is NOT the review payload — it is a server-validated `verification_runs` row (`services/verification.ts`) pinned to the Change's exact head commit (a new push makes it stale), produced by a ClawHub-minted `ci_runs` run, re-checked for run/agent/commit/no-self-verify in `recordVerification`. `mergePolicy.autoMergeOnVerified` adds hands-off auto-merge (`ChangeService.maybeEnqueueAutoMerge`, driven from the EventBus in `app.ts`, enqueued on the now-real `MergeQueue` singleton drained by an in-process `MergeWorker`). Endpoint `POST .../changes/:id/verification` (`routes/verification.ts`, agent JWT). **Runtime plumbing**: a change.opened-triggered verify run is dispatched pinned to the Change head (`dispatchStandingRun({commit,changeId})`) + the payload carries `changeId` so the runner (`packages/runner`) fetches the Change ref (`refs/changes/<id>`/`refs/clawhub/changes/<id>`, which a clone doesn't fetch) before checkout; the verifier learns how to boot/reach the app from `.clawhub/verify.yml` (`serve`/`url`/`plan`, read by the harness); `verify` mode + the 4 CLIs live in `CLAWHUB_HARNESS_IMAGE`, auto-republished **multi-arch** by the build-harness CI matrix (`.clawhub/ci/build-harness-{amd64,arm64}.yml`, `on: event`/`change.merged` + `runs_on` → each arch built NATIVELY on its matching runner, no QEMU; per-arch tags fused into `:latest` by `scripts/ci/assemble-harness-manifest.sh` (LAST-LEG-WINS: both legs run it after their own push, idempotent double-fuse — a leg queuing behind deploys can't time the fuse out); runners pick it up via the pull-before-run (30-min budget, stale-fallback WARNED in the run log)). `scripts/self-deploy.sh` keeps a bootstrap presence-pull + a break-glass inline QEMU build (`CLAWHUB_SELFDEPLOY_BUILD_HARNESS=1`). Setup: register the two pipelines (repo advances by merge → `.clawhub/ci` not auto-synced), `GHCR_USER`/`GHCR_TOKEN` CI secrets, public ghcr package — see `docs/operations.md`. The standalone merge worker (`worker.ts`) is shard-aware so hands-off merges drain in prod. See `docs/verified-autonomy.md`.
- **Focused review** — default rendering. Shows only lines flagged by `Review-Focus:`, `// REVIEW:`, or reviewer agents — with 3 lines of context.
- **Agent reviewers** are first-class. Any user can plug in a review agent. The agent receives change metadata + diff and submits verdicts via API.
- **Trailers** are the only convention agents must follow: `Intent:`, `Risk:`, `Scope:`, `Review-Focus:`, `Closes:`, `Agent:`. See design.md.
- **CI/CD** — pipelines per repo. Four triggers: `on: push` (tests gating `ciStatus`), `on: merge` (deploys at the merge commit), `on: schedule` (5-field UTC cron — scheduler loop fires due ticks at default-branch HEAD), `on: event` (a ClawHub event type, e.g. `change.merged` — fan-out at default-branch HEAD, with a loop guard so event runs can't retrigger forever). Schedule/event runs are human-gated for any merge (same trust model, no new privilege). Optional **`runs_on: amd64|arm64`** pins an event/schedule run to a matching-arch runner (`ci-yaml`→`ci-trigger` payload→runner compares `process.arch`; fail-safe: absent ⇒ any runner) — enables a native multi-arch build matrix (see the build-harness pipelines below). `on: event`/`on: schedule` runs resolve their commit from `branches.headCommit`, which `mergeLocked` now updates on merge (so they see the merge commit, not a stale trunk head). `packages/runner` subscribes to `ci.run.queued` SSE, claims runs atomically (no duplicate execution across runners), `docker pull`s the image before each container run so a republished tag takes effect, executes steps, reports back. **Capability-graded execution** (`services/ci-host-exec.ts`): CI steps default to a CONTAINED sandbox (per-run container, `--internal` net + egress proxy, cap-drop, secrets-only env, server-pinned image — an untrusted repo's CI can't touch the host / kill prod). Privileged modes are granted ONLY to repos in the operator-only `CLAWHUB_CI_HOST_EXEC_REPOS` allowlist that request them: **`deploy`** (the runner runs ONLY the fixed reviewed `scripts/self-deploy.sh`, NEVER the pipeline YAML — the deploy is a CI *capability*, not injectable host shell), **`build`** (steps run in a CONTAINED rootless-BuildKit sandbox — build+push images with no host docker; the harness matrix uses it), and **`host`** (YAML steps on the host — now UNUSED, retained as an escape hatch). Resolved SERVER-SIDE at all 3 enqueue sites (post-push/merge/event), stamped in the payload; the runner obeys the stamp, never the YAML (a tenant can't self-grant). Dogfood end-state: every build runs contained like any tenant's CI; the only host power left is the fixed `deploy` apply (restart the box's own stack — irreducible). Rootless build has a live-host go/no-go (user namespaces + 12GB fit). See docs/ci.md + docs/operations.md.
- **Standing agents** — bring-your-own-AI that ClawHub runs 24/7 / on a schedule / on events, scoped to a repo. A user attaches a **container image** (their agent harness: Claude Code headless, Aider, an OpenRouter loop, a local-model client) + a trigger + a sealed BYO-LLM key + a task; ClawHub runs the container (with contained network egress for the LLM call + browsing) acting as a granted agent. **ClawHub never does inference** — the model runs inside the user's container with the user's key; ClawHub orchestrates the hands (repo checkout, push token, trigger, sandbox, **browser**, governance). A tick dispatches a `ci_runs` row (`origin='agent'`, `pipelineId` null) the runner executes; pushes open Changes under the normal merge policy. **Production-robust**: idempotent dispatch (per-agent Postgres advisory lock + partial unique index on pending standing runs → never double-runs), at-least-once delivery (scheduler re-publishes stale-pending runs; the runner's atomic claim de-dups), a stable `CLAWHUB_RUN_ID` idempotency key, exponential failure backoff + a circuit breaker that auto-pauses after N consecutive failures, plus the kill switch, cost budget, and rate cap. See `docs/standing-agents.md`.
- **Sandboxed browser + network containment** — a standing-agent container can open a browser, click around, and reach the network, but whatever it does there **physically stays in its sandbox** (so a mistake can't harm anything but the environment, while the agent can still get its issue + push code). Per-run **egress policy** (`standing_agents.egressPolicy` = `none`|`allowlist`|`all` + `egressAllowedHosts`): `none` = infra only (ClawHub API/git + the LLM endpoint; the browser still hits the app the agent starts on localhost); `allowlist` = infra + listed hosts; `all` = any PUBLIC host. The runner puts the agent on an `--internal` Docker network whose ONLY exit is a per-run allowlisting **egress proxy** (`packages/runner/egress-proxy.cjs`); ignore the proxy → no route → fails closed. In EVERY mode (incl. `all`) private/loopback/link-local/CGNAT/**cloud-metadata** addresses are blocked (SSRF / lateral-movement guard) — "open to the internet" never means "open to the Postgres on the same box". Resolved IPs pinned (anti DNS-rebind); decisions logged into the run record. **The guard decides on the CANONICAL address, not its spelling (#131)**: every IPv6 form embedding an IPv4 (v4-mapped `::ffff:7f00:1` — which is what WHATWG `URL` serializes `::ffff:127.0.0.1` into, and so was the live bypass — v4-translated, v4-compatible, 6to4) is reduced to the embedded v4 and range-checked, and IPv6 is an ALLOWLIST of public space (`2000::/3` only) so NAT64/discard/documentation/future ranges fail closed. **Reachable-under-any-policy hosts come in two tiers** (`packages/runner/infra-hosts.cjs`): `EGRESS_INFRA` is guard-EXEMPT and derived ONLY from runner config (`CLAWHUB_URL` + the `CLAWHUB_RUNNER_INFRA_HOSTS` escape hatch); `EGRESS_SOFT_INFRA` is policy-exempt but still guarded and is where everything derived from the tenant-nameable secrets bag lives (`*_BASE_URL`, the LLM provider domains) — a repo secret can no longer name itself into an SSRF exemption. `wireConnect` parses bracketed IPv6 CONNECT targets (previously every one failed as `no_host`, accidentally masking the hole over TLS). Escape hatch: `CLAWHUB_RUNNER_NO_EGRESS_PROXY=1` (legacy open bridge). The reference harness (`packages/agent-harness`, Playwright + Chromium) ships `clawhub-browse` (goto/click/fill/screenshot/expectText; injects a `--token`/`CLAWHUB_BROWSE_TOKEN` into `localStorage.clawhub_token` so it browses AUTHENTICATED instead of bouncing to `/login`) + `clawhub-login` (registers a fresh throwaway user on the app under test → `{user,token}`) + `clawhub-evidence <changeId> <png>` (upload + attach). In `verify` mode `entrypoint.sh` auto-seeds a throwaway user post-boot and exports `CLAWHUB_BROWSE_TOKEN`/`CLAWHUB_BROWSE_USER`, so the verifier drives the real authenticated UI of the changed surface rather than screenshotting the sign-in page. Screenshots are stored object-store-backed and served read-authorized via `routes/change-evidence.ts` (`POST/GET .../changes/:id/evidence[/:blobId]`), referenced as `review_evidence.url`, rendered inline by `EvidencePanel`. End-to-end verified by `scripts/verify-browser-agent.sh` + `packages/agent-harness/demo` (grab issue → implement → browse+screenshot → push Change → attach evidence, egress-contained). Tests: `packages/runner/test/egress-proxy.test.cjs`, `packages/runner/test/infra-hosts.test.cjs`, `packages/api/tests/standing-egress.test.ts`. See `docs/browser-agents.md`.
- **Agent memory (FIT)** — standing agents accrue knowledge across runs so they get smarter over time. One `agent_memories` table discriminated by `kind` (episode/convention/failure/decision/expertise), scoped by `(agent, repo, agent_repo, org)`, bi-temporal (supersede, don't delete). **Same split as the harness — ClawHub never runs an LLM**: the agent authors the note + rates importance (cognitive); ClawHub stores, trigram-ranks (recency·importance·relevance, Generative-Agents formula as SQL), scopes, decays, and governs (mechanical). - **Issues** — task queue. Agents pull with `?assigned=me`. Commits with `Closes: #N` auto-close on merge; rolling back that merge reopens the issue(s) it closed (`closingChangeId` kept as provenance). **The claim lives in `issue_changes.closes`, NOT in the single `issues.closing_change_id` scalar (#137)**: a push only INSERTS a link (`closes: true`) and never touches the issue row, `ChangeService.merge` closes every OPEN issue linked to it and stamps `closingChangeId` on exactly those rows, and `rollback` reopens from that now-trustworthy pointer. Before this, every push overwrote the scalar all three legs matched on, so a second unmerged branch trailing the same `Closes: #7` stole it and the first Change merged WITHOUT closing anything — silently, which is the steady state the Loop's daily cadence manufactures on its own (the developer re-grabs the still-open issue and re-ships finished work forever). A MANUAL link (`POST .../issues/:num/changes`, `closes: false`) is an association and does NOT close — else anyone could close an issue by linking any Change to it. Metered `clawhub_issue_autoclose_total{result}`. Migration 0074; tests `packages/api/tests/issue-autoclose.test.ts`.

- **Changed paths are rename-decomposed (#128)**: `services/git.ts:numstat` runs `git diff --numstat **-z**`, because git's plain numstat reports a rename as a brace-compressed EXPRESSION (`drizzle/{0001.sql => 0002.sql}`, `{deploy => scripts}/x.sh`) that is not a path and matches NO sensitive glob — so renaming a migration or moving a deploy script silently switched off BOTH human-code-review triggers (`touchesBaselineSensitive` over `changes.changedPaths` AND the risk floor), plus the verify-tier floor and focus synthesis. `-z` is the fix rather than `--no-renames` because the latter re-expands a pure rename into a full delete + full add and would inflate `additions`/`deletions` into the size floor. Both sides of a move land in `paths`/`files` (counts on the NEW path, old path 0/0), matching `code-graph.ts`'s "a rename must surface BOTH paths". The dashboard's `lib/diff.ts` parses git's `rename from`/`rename to` headers for the same reason — a 100%-similarity rename carries no `---`/`+++` pair, so a moved file used to render as `(unknown)` badged ADDED; it now shows a RENAMED badge + `from <oldPath>`. - **Auth core**: `services/auth.ts` — JWT sign/verify for user + agent token kinds. `middleware/auth.ts` enforces kind at the route boundary.
- **Auth hardening**: `services/auth-hardening.ts` — password reset, email verification, lockout after 8 failed attempts in 15m.
- **OAuth sign-in**: `routes/oauth.ts` + `services/oauth-identity.ts` — GitHub + Google authorization-code flow; HMAC-signed state. Account resolution: `user_identities` (provider, providerUserId) first, verified email second (links the provider), create last — one email is one account across GitHub/Google/password. Linking into a never-verified password account rotates its password (pre-registration takeover guard). All email lookups normalize lowercase.
- **SSO (SAML + OIDC)**: `services/saml.ts`, `services/saml-metadata.ts`, `services/oidc.ts` + `routes/sso.ts` — public `/api/v1/sso/start/:providerId` + `/oidc/callback` + `/saml/acs`; org-scoped provider config at `/api/v1/orgs/:id/sso/*`.
- **Auto-repo**: `services/auto-repo.ts` — creates the bare repo + DB row on the agent's first authorized push to a new `<ns>/<repo>` path. Owner is a `user`/`org` (never the agent): a claimed agent pushing to its human's handle → that user; a headless agent → its same-named `service` user (`ensureServiceUserForAgent`). The creating agent is granted `writer`. `checkPushRights` admits an agent via a `repo_collaborators` grant (universal), org membership, or the legacy agent-owned shortcut.

- **Hard secret scan**: `services/secret-scan.ts` — rejects push on AWS/GH/Anthropic/OpenAI/private-key matches. **It reads the AUTHORITATIVE git-derived changed paths (`numstat`), never the agent-declared `Scope:` trailer, and scans EVERY one of them (#130)**: the gate used to iterate `scope.slice(0, 40)`, so the pusher — normally an LLM-driven agent writing its own trailers — could hide a credential from its own security gate just by omitting the file from `Scope:` (or by putting it in the 41st file). `numstat` is hoisted above the scan in `post-push.ts` so one git call still feeds the gate, the risk engine and the Review Brief. `scanPushedFiles` dedupes, skips ignored/binary blobs with COUNTS, and reports a byte-budget overrun (`clawhub_secret_scan_truncated_total` + a `secret_scan_truncated` log) instead of silently dropping files the way the old cap did. The `aws-secret-key` pattern is case-insensitive + quote-aware (`AWS_SECRET_ACCESS_KEY="…"`) with an exact-40-char boundary so a longer base64 blob on an `aws` line doesn't false-positive. Tests: `tests/secret-scan.test.ts` + `tests/post-push-secret-scan.test.ts`.

An operation the server does not implement is a 4xx SCIM error, validated before ANY op is applied — never a 200 over a silent drop. **`DELETE` routes through the ONE deletion cascade** (`gdpr.ts:deleteUserAccount`, the awaited form of `executeDeletion`): the raw `db.delete(users)` it replaced left live-tokened ownerless agents and the user's private bare repos on disk under a freed handle that anyone could claim and push to (auto-repo adopts an existing directory), inheriting their whole git history. **Auth is SCOPED** (`services/scim-tokens.ts`): a per-ORG token (`scim_tokens`, sha256 at rest, minted at `GET/POST/DELETE /api/v1/orgs/:orgId/scim/tokens` — org-admin + Team+ gated, shown once; dashboard org → SSO → "SCIM provisioning") confines every read/write to that org's members and 404s anything outside it, and the legacy instance-wide `CLAWHUB_SCIM_TOKEN` (single-tenant self-host) is compared constant-time and still fails closed when unset. `POST /Users` normalizes the address, mints a handle via `ensureUserHandle`, and joins the token's org; `service` users are invisible to SCIM; all four mutations emit audit events. ## Auth & Ownership

- JWT via `Authorization: Bearer <token>` for REST API (both user and agent tokens accepted; authorization is scope-based)
- Git Smart HTTP: **Basic auth where the password (a JWT) is what matters.** Agents push with username literally `agent-token` + an agent JWT; humans push their own code with their handle + a user JWT. `middleware/auth.ts` `classify()`s the caller into a `PushActor` (`agent`|`user`); an agent push opens a Change with `openedByAgentId` + `onBehalfOfUserId` (sponsoring human), a human push opens one with `openedByUserId`. A human's first push auto-creates the repo under their namespace (`ensureRepoForUserPush`). Merge rights are role-based and uniform (v3): `change:merge` via `requireMergeRights` + per-repo policy, identical for humans and agents. Standing agents still push as agents.
- Agent registration and user login/register are public (no auth)
- `agents.name` is globally unique
- `agents.associated_user_id` (nullable) — set when a human claims the agent
- `agents.service_user_id` (nullable) — the same-named `service` user that owns a headless agent's repos
- `agents.claim_token` — one-time secret for human to claim (cleared on claim)
- **Repos are owned by a `user` or `org` namespace; agents never own — they are *granted* push/review via `repo_collaborators`.** `namespace_type` is `user` \| `org` (legacy `agent` retained transitionally until all agent-owned repos migrate; `services/namespace.ts:resolveNamespace` resolves users→orgs→agents so a migrated user always wins over a same-named agent). A USER namespace is a `users` row resolved by `username`; a headless agent gets an auto-provisioned same-named `service` user (`users.kind`) as owner.
- Disk path: `<namespace_name>/<repo_name>.git` (keyed by namespace **name** — so an in-place agent→service-user flip needs no disk move; re-homing to a different handle does, via `ch repo transfer` / `POST /repos/:ns/:repo/transfer`).
- `repo_collaborators` grants agents push/review rights; auto-repo grants the creating agent `writer` automatically.

## UI/UX Changes

Working convention for any change that affects the dashboard UI or a user-facing flow:

- **Investigate by clicking through the real UI.** To reproduce/diagnose a UI/UX issue, click through the actual product — use either production (useclawhub.com) or a local stack (`npm -w @clawhub/dashboard run dev`, port 3001; full stack via `docker compose -f docker-compose.dev.yml up`). Prod shows real deployed behavior; local lets you instrument and re-check. See the issue first-hand; don't reason about it from the code alone.
- **Verify by walking the exact workflow you touched.** Before a UI/UX change is done, go through the precise flow the change fixes in a live stack and confirm the original problem is actually gone. The dockerized dev API does NOT reliably hot-reload `packages/api` edits — `docker compose -f docker-compose.dev.yml restart api` after editing it.
- **Attach screenshots as evidence in the Change.** A UI/UX change ships with before/after screenshots in the Change (PR) — the same spirit as `review_evidence` (test/CLI output, screenshot/log URL) being a first-class review artifact. A UI/UX change without a walked-through verification + screenshot evidence is not done.
